# Historias de Usuario - Identidad y Acceso (IAM)

Esta sección presenta las Epics e Historias Técnicas identificadas para el módulo de Identidad y Acceso (IAM).

## Epics

| Epic / Story ID | Título | Descripción | Criterios de Aceptación | Relacionado con (Epic ID) |
| --------------- | ------ | ----------- | ----------------------- | ------------------------- |
| WS-EP-01         | Gestión de Identidad y Acceso | Como Visitante o Usuario, quiero registrarme y autenticarme en la plataforma, para poder acceder de forma segura a mis dispositivos y configuraciones. | La Epic se completa cuando todas las historias de usuario relacionadas han sido implementadas, validadas y aceptadas. | - |

## Historias Técnicas

| Epic / Story ID | Título | Descripción | Criterios de Aceptación | Relacionado con (Epic ID) |
| --------------- | ------ | ----------- | ----------------------- | ------------------------- |
| WS-US-01        | Iniciar Registro de Usuario | Como Desarrollador, quiero iniciar el registro de un nuevo usuario a través de una API, para crear una sesión de validación temporal y despachar un código de verificación. | Escenario: Registrar usuario exitosamente<br>Dado que el endpoint "/api/v1/auth/sign-up" está disponible<br>Cuando se envía una petición POST con los campos de `firstName`, `lastName`, `email` y `password`<br>Entonces se recibe una respuesta con estado 201 conteniendo el ID de sesión del registro en el cuerpo.<br><br>Escenario: Intentar registrar con campos inválidos<br>Dado que el endpoint "/api/v1/auth/sign-up" está disponible<br>Cuando se envía una petición POST con un formato de email inválido o sin contraseña<br>Entonces se recibe una respuesta con estado 400. | WS-EP-01 |
| WS-US-02        | Confirmar Registro de Usuario | Como Desarrollador, quiero confirmar un registro de usuario validando el código de verificación a través de una API, para persistir definitivamente la cuenta del usuario. | Escenario: Confirmar registro con código de verificación válido<br>Dado que el endpoint "/api/v1/auth/confirm" está disponible<br>Cuando se envía una petición POST con el `sessionId` and `code` correcto<br>Entonces se recibe una respuesta con estado 201 y los datos del usuario creado en el cuerpo.<br><br>Escenario: Intentar confirmar con código vencido o incorrecto<br>Dado que el endpoint "/api/v1/auth/confirm" está disponible<br>Cuando se envía una petición POST con un `code` incorrecto o una sesión expirada<br>Entonces se recibe una respuesta con estado 400. | WS-EP-01 |
| WS-US-03        | Iniciar Sesión con Contraseña | Como Desarrollador, quiero autenticar las credenciales de correo y contraseña a través de una API, para emitir los tokens de acceso JWT. | Escenario: Inicio de sesión exitoso con credenciales correctas<br>Dado que el endpoint "/api/v1/auth/sign-in" está disponible<br>Cuando se envía una petición POST con `email` y `password` correctos de un usuario verificado<br>Entonces se recibe una respuesta con estado 200 conteniendo los tokens JWT de acceso y refresco.<br><br>Escenario: Intentar inicio de sesión con credenciales inválidas<br>Dado que el endpoint "/api/v1/auth/sign-in" está disponible<br>Cuando se envía una petición POST con datos de contraseña incorrectos o cuenta no verificada<br>Entonces se recibe una respuesta con estado 401. | WS-EP-01 |
| WS-US-04        | Autenticar mediante Token de Google | Como Desarrollador, quiero autenticar usuarios mediante su ID token de Google OAuth a través de una API, para permitir inicios de sesión directos federados. | Escenario: Autenticación federada exitosa con Google<br>Dado que el endpoint "/api/v1/auth/google/sign-in" está disponible<br>Cuando se envía una petición POST con un `idToken` de Google verificado y válido<br>Entonces se recibe una respuesta con estado 200 y los tokens JWT de la plataforma en el cuerpo.<br><br>Escenario: Autenticación de Google con token inválido<br>Dado que el endpoint "/api/v1/auth/google/sign-in" está disponible<br>Cuando se envía una petición POST con un token de Google inválido o vencido<br>Entonces se recibe una respuesta con estado 401. | WS-EP-01 |
| WS-US-05        | Iniciar Flujo de Autorización de Google | Como Desarrollador, quiero iniciar el flujo de autorización de Google OAuth a través de una API, para redirigir al usuario al formulario de consentimiento oficial de Google. | Escenario: Redirección al consentimiento de Google exitosa<br>Dado que el endpoint "/api/v1/auth/google/authorize" está disponible<br>Cuando se realiza una petición GET<br>Entonces se recibe una respuesta con estado 302 redireccionando al usuario a la URL de Google OAuth. | WS-EP-01 |
| WS-US-06        | Procesar Callback de Google OAuth | Como Desarrollador, quiero recibir y procesar el código devuelto por Google en el callback a través de una API, para generar las credenciales de acceso y devolver al usuario al frontend. | Escenario: Procesar callback y redirigir al frontend con éxito<br>Dado que el endpoint "/api/v1/auth/google/callback" está disponible<br>Cuando se recibe una petición GET con los parámetros correctos de `code` y `state`<br>Entonces se recibe una respuesta con estado 302 redirigiendo a la pantalla del frontend con los tokens JWT en los parámetros de consulta.<br><br>Escenario: Fallo en validación de callback de Google<br>Dado que el endpoint "/api/v1/auth/google/callback" está disponible<br>Cuando el parámetro `error` está presente o el `state` es inválido<br>Entonces se recibe una respuesta con estado 302 que redirige a la pantalla de error del frontend. | WS-EP-01 |
| WS-US-07        | Cerrar Sesión del Usuario | Como Desarrollador, quiero revocar la validez de los tokens del usuario a través de una API, para asegurar el cierre de sesión de la cuenta. | Escenario: Cerrar sesión exitosamente revocando tokens<br>Dado que el endpoint "/api/v1/auth/sign-out" está disponible<br>Cuando se envía una petición DELETE con el encabezado de autorización conteniendo el token de acceso Bearer<br>Entonces se recibe una respuesta con estado 204 y los tokens son inhabilitados.<br><br>Escenario: Intentar cerrar sesión sin token de autorización<br>Dado que el endpoint "/api/v1/auth/sign-out" está disponible<br>Cuando se envía una petición DELETE sin cabecera de autorización o token inválido<br>Entonces se recibe una respuesta con estado 401. | WS-EP-01 |
| WS-US-08        | Refrescar Token de Acceso | Como Desarrollador, quiero emitir un nuevo token de acceso a partir de un token de refresco válido a través de una API, para extender el tiempo de sesión del usuario. | Escenario: Rotar y refrescar token exitosamente<br>Dado que el endpoint "/api/v1/auth/refresh" está disponible<br>Cuando se envía una petición POST con un `refreshToken` válido<br>Entonces se recibe una respuesta con estado 200 con el nuevo token de acceso y un nuevo token de refresco rotado.<br><br>Escenario: Refrescar con token inválido o expirado<br>Dado que el endpoint "/api/v1/auth/refresh" está disponible<br>Cuando se envía una petición POST con un `refreshToken` vencido o inválido<br>Entonces se recibe una respuesta con estado 401. | WS-EP-01 |
| WS-US-09        | Verificar Validez del Token | Como Desarrollador, quiero validar la vigencia de un token de acceso a través de una API, para permitir la verificación de sesiones en servicios externos. | Escenario: Validar token de acceso exitosamente<br>Dado que el endpoint "/api/v1/auth/verify" está disponible con cabecera `Authorization` Bearer<br>Cuando se envía una petición GET con un token de acceso activo<br>Entonces se recibe una respuesta con estado 200 conteniendo los metadatos de validez, `userId` y expiración en el cuerpo.<br><br>Escenario: Validar token vencido o ausente<br>Dado que el endpoint "/api/v1/auth/verify" está disponible<br>Cuando se envía una petición GET sin cabecera de autorización o con un token inactivo o inválido<br>Entonces se recibe una respuesta con estado 401. | WS-EP-01 |
